# Getting Started

> **Audience:** new contributors. Assumes basic familiarity with
> Java 25, Spring Boot, and Vue 3.
> **Scope:** the fastest path from a fresh clone to a working
> dev environment. For day-to-day commands see
> [`AGENTS.md`](../../AGENTS.md). For testing see
> [`testing.md`](./testing.md).

## 1. Prerequisites

- **Java 25** (Temurin recommended). One version everywhere: the pom compiles
  with `<release>25</release>`, the CI workflows, the Docker image and the
  desktop runtime (`scripts/build-desktop.*`) use Temurin 25; the CI uses
  Node 24 like the Docker image
- **Maven 3.9+**
- **Node.js** `^20.19.0 || >=22.12.0` (per `package.json:engines`)
- **Docker** with Compose v2 (for the full-stack dev DB and
  containerised builds)
- **Git**

The frontend has no native-build dependency. The backend has no
native-build dependency either; `java.awt.headless=true` is set
in the Docker entrypoint to suppress AWT display access.

## 4. Start the database

For the **dev workflow** (recommended — full demo data 2023-2026):

```bash
cd backend
docker compose up -d postgres
```

This starts an empty development PostgreSQL on `localhost:5432` with the
credentials from `backend/docker-compose.yml` (`billery` / `billery123`); the backend creates
the schema with Flyway when it starts (step 5). To get the full 2023-2026
demo dataset (100 customers, 30 articles, 30 services, 15 equipment, 1 420 documents,
~3 700 line items, ~3 500 history entries, ~400 payment rows), put this into `backend/.env`:

```env
LOAD_DEMO_DATA=true
```

The backend then loads `dummies.sql` on start, but only into a database
without customers, so your own data is never overwritten and the load runs
once per volume.

To re-seed from scratch, drop the volume and restart the backend:

```bash
cd backend
docker compose down -v
docker compose up -d postgres
```

For the **full-stack / production-like layout** (root compose, no
demo dummies — schema only):

```bash
# from the repo root
cp .env.example .env
# Set DB_PASSWORD to a new non-default secret in .env before starting:
docker compose up -d
```

This starts PostgreSQL and the backend; the backend migrates the empty
database with Flyway, so the customer table is empty. It never loads demo
data unless `LOAD_DEMO_DATA=true` is set. Use this for
behaviour tests where you want a clean DB. Before you can render a PDF,
enter the company data (Inhaber); without it the download answers with
a message instead of a document.

## 5. Start the backend

```bash
cd backend
SPRING_PROFILES_ACTIVE=dev mvn spring-boot:run
```

The backend starts on `http://localhost:8080`. On first start it
runs Flyway (`SchemaMigrator`: creates the schema from
`db/migration/V1__baseline.sql` on an empty database and applies later
migrations); `DatabaseMigration.runMigrations` (idempotent delta
migrations) only does something on H2. Health check: `GET http://localhost:8080/api/health`.
Swagger UI: `http://localhost:8080/swagger-ui.html`.

## 6. Start the frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Vite serves the SPA on `http://localhost:5173`. The dev server
proxies nothing — the API base URL is configured by
`VITE_API_BASE_URL` (default `http://localhost:8080`).

## 7. Issue a test invoice

1. Open `http://localhost:5173`.
2. **Owners** → fill in your company details (the "Inhaber" form).
3. **Customers** → add a test customer.
4. **Articles & Services** → add a test article or service.
5. **Templates** → review the default templates (the seed
   templates in `V1__baseline.sql` are loaded on first start).
6. **Invoices** → create an invoice, pick a customer, add line
   items, save.
7. Click **Export PDF** → `GET /api/invoices/{id}/pdf` returns the
   PDF generated by Flying Saucer from the block template.
