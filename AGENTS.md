# AGENTS.md

Architecture docs live in [the `docs/` tree](./docs/README.md) (in
particular [`docs/architecture/`](./docs/architecture/),
[`docs/guides/`](./docs/guides/), and
[`docs/reference/`](./docs/reference/)). The class / package index
is generated by Doxygen (`Doxyfile`), the REST API by SpringDoc
(`/swagger-ui.html`), and CI behaviour is defined by
`.github/workflows/*.yml` — none of these are duplicated in prose.
This file covers what an agent would likely get wrong.

## Monorepo Layout

| Path | What |
|------|------|
| `backend/` | Java 25 / Spring Boot backend |
| `frontend/` | Vue 3 / Vite frontend |
| `app-desktop/` | Tauri 2 desktop shell (Rust + thin Node wrapper) |
| `XRechnung/` | Notes on the XRechnung specification and the KoSIT validator; the validator itself is fetched by `scripts/fetch-kosit-validator.sh` (CI job `xrechnung`) |

All commands below assume you `cd` into the relevant subdirectory first.

## Commands (verified)

### Backend (`backend/`)

```bash
mvn test                 # run tests
mvn spotless:apply       # auto-format (Google Java Format, version pinned in pom.xml)
mvn spotless:check       # bound to `verify`: CI fails on formatting
mvn pmd:check            # bound to `verify`: CI fails on PMD violations
mvn -Pdesktop,openapi verify -DskipTests   # writes target/openapi.json (starts the app on :18080)
mvn -Psaas test          # the SaaS build: SaaS code + migrations, suite runs with the Spring profile saas (needs POSTGRES_TEST_URL; run `mvn clean` when switching between the default and the saas build)
mvn spring-boot:run      # start dev server (port 8080)
mvn clean install -DskipTests  # full build, skip tests
```

PMD rules live in `backend/pmd-ruleset.xml`.

### Frontend (`frontend/`)

```bash
npm run dev              # Vite dev server (port 5173)
npm run build            # production build
npm run test:run         # single Vitest run
npm run test:coverage    # Vitest with V8 coverage
npm run test             # Vitest in watch mode
npm run test:e2e         # Playwright smoke suite against E2E_BASE_URL (default :5173); see e2e/README.md
```

**There is no `npm run lint` or `npm run typecheck`.** The project uses JavaScript (no TypeScript), has no ESLint, and no Prettier. `frontend.yml` runs `npm run test:run` and `npm run build` in CI.

### Desktop shell (`app-desktop/`)

Tauri 2 wrapper around the running Spring Boot backend. Rust crate with a thin
`package.json` that owns the `@tauri-apps/cli` and exposes `build` / `dev`
scripts delegating to `../frontend`.

```bash
npm install              # one-time, fetches @tauri-apps/cli
npm run build            # builds the Vue frontend (via cd ../frontend)
npm run dev              # starts the Vite dev server (via cd ../frontend)
npx tauri build          # full installer build (calls beforeBuildCommand = "npm run build")
npx tauri dev            # dev run; window opens at http://127.0.0.1:8080
```

**The Tauri window points at `http://127.0.0.1:8080` (the bundled backend), not
an embedded SPA build** — `tauri.conf.json` has `frontendDist` set so the
bundler can resolve at install time, but the runtime webview loads the backend
URL. The backend binds to `127.0.0.1` only (desktop mode has no auth). The port
stays fixed because stored logo URLs contain it; `src/lib.rs` therefore refuses
to start (error page) when something else already answers on 8080, and only
trusts a `/api/health` response carrying its per-launch `DESKTOP_INSTANCE_ID`.
On exit it calls `POST /api/desktop/shutdown` (token-protected) so H2 closes
the database file cleanly, and kills the JVM only after a 10 s grace period.
There is no Rust toolchain requirement for the backend build, but `cargo check`
must pass for `src/lib.rs` changes. The bundled `app.jar` (Spring Boot fat JAR) and `resources/runtime/`
(jlink'd JRE) are produced by `scripts/build-desktop.sh` / `build-desktop.ps1`,
not by `npm run build`, and are never committed (`app-desktop/.gitignore`; `resources/.gitkeep`
keeps the directory Tauri bundles, so `cargo check` works on a fresh clone).
`gen/schemas/*.json` is auto-generated by Tauri and committed.

## Tech Stack (non-obvious points only)

Versions are in `backend/pom.xml` and `frontend/package.json`; don't copy them here.

- **Vue Router 5** is intentional; do **not** downgrade to 4.x.
- **Tests:** JUnit Jupiter + H2 in `MODE=MariaDB` by default, the whole suite on a real PostgreSQL when `POSTGRES_TEST_URL` is set (CI job `postgres`); no Spring context in unit tests. Tests build repositories, services and controllers through `TestWiring` (test sources), which mirrors the production constructor injection; when a constructor changes, only `TestWiring` follows. `TestMoney` holds `bd(...)` / `assertAmount(...)` for `BigDecimal` amounts (never compare amounts with `BigDecimal.equals`: it also compares the scale).
- **Path alias:** `@` → `./src` (jsconfig.json).
- **Design system:** colours, spacing, radii, type and z-index are tokens in `frontend/src/styles/tokens.css`; shared classes (`.btn` + `.btn-primary` …, `.form-control`, `.data-table`, `.badge-*`, modal shell) are in `styles/components.css`. A `.vue` file uses `var(--color-…)`, never its own hex / rgb literal: `styles/colorLiterals.spec.js` fails on any hex / rgb / hsl literal in a style block (`colorLiterals.baseline.json` is empty after the migration; the template editor's document preview is exempt, its colours come from the template, and the preview sheet uses `--color-paper`). Do not define `.btn-primary` and friends in a component. Details: `docs/architecture/frontend.md > Design system`.
- **No Bean Validation:** there is no `@Valid` and no validation starter; controllers check input by hand.
- **OpenAPI spec:** the `openapi` Maven profile starts the app (in-memory H2, port 18080) with `spring-boot:start`, lets `springdoc-openapi-maven-plugin` fetch `/v3/api-docs`, then stops it. Needs `-Pdesktop` for H2.
- **Desktop installers** are built by Tauri via `scripts/build-desktop.sh`; there is no jpackage path.

## Architecture Gotchas

- **JDBC repositories on `JdbcClient`** — no Spring Data, no JPA/Hibernate. The 11 repositories are `@Repository` beans that get Spring's `JdbcClient` by constructor and write their own SQL with named parameters and `RowMapper` constants; controllers and services get them by constructor injection (never `new`). `DbConfig` defines the pooled `HikariDataSource`, the `JdbcClient`, the transaction manager and the `TransactionTemplate`, and hands the pool to `Database.useDataSource(...)`. `Database` itself is only the connection-settings holder plus `getConnection()` for the pre-Spring bootstrap (`MainApp.prepareDatabase()`, `DatabaseInitializer`, `DatabaseMigration`), which runs on a `DriverManagerDataSource` before the pool exists.
- **Repositories never swallow SQL errors.** Every `JdbcClient` call runs inside `run("operation", () -> ...)` (`BaseRepository`), which turns Spring's `DataAccessException` into a logged, unchecked `DatabaseException` (plain JDBC code uses `throw databaseError("operation", e)`). `ApiExceptionHandler` maps it — and a failed commit (`TransactionException`) — to HTTP 500 with a JSON `{"message": ...}`. Returning `null` means "not found", never "failed". Generated ids are read with `generatedId(keyHolder)` (PostgreSQL and H2 may return further generated columns, so the `id` column is preferred).
- **Transactions:** multi-statement writes run in `transactions.execute(status -> ...)` on the `TransactionTemplate` injected by constructor — **not** `@Transactional`, because the tests run without a Spring context and the annotation would silently do nothing there. Every `JdbcClient` call inside joins the transaction; nested calls join the outer one, and a nested failure the caller handles does not doom the outer transaction (`DbConfig.newTransactionManager`). `DocumentService.create/update/cloneDocument`, all `InvoiceLifecycleService` writes (issue, payments, cancel, draft delete), the template write endpoints and `DocumentNumberSeriesRepository.getNextNumber` use it; the reserved document number is rolled back with a failed save (no gaps). Inside a transaction `Database.getConnection()` returns the bound connection with `close`/`commit`/`rollback`/`setAutoCommit` disabled.
- **List endpoints load in batches.** `InvoiceController.convertAllToDto` fetches customers, items, payment sums and credit notes with one query each for the whole list; never add a per-document query to it (1 420 demo documents → thousands of round trips). Single-document endpoints use `convertToDto`; a test asserts both produce identical DTOs. **The document list (`InvoicesView`) is paged on the server:** `GET /api/invoices/page` filters and orders in SQL (`InvoiceListQuery`) and converts only the page (`convertPageToDto`, id-scoped batch queries). Its status filters mirror `useDocumentType.applyStatusFilter` / `isInvoiceOverdue` / `isOfferExpired`; change both sides together. The view drops responses of superseded requests and debounces the search (300 ms). **The dashboard** loads `GET /api/invoices/statistics` (figures) and `GET /api/invoices/page` with `from`/`to`, `includeArchived=true` and the status keys `issued` / `paid` / `open` (first five rows); its card "unbezahlt" maps to `open` (sent or partly paid). `InvoiceStatisticsService` uses only period-scoped batch queries; keep it that way. There is no unpaged document or customer list endpoint; a new screen pages too. **Customers likewise:** the customer list and the document form's `CustomerPicker` use `GET /api/customers/page` (server search, `sort=name` for the picker). `BaseRepository.containsPattern` builds the case-insensitive, `%`/`_`-literal LIKE pattern for both searches.
- **Startup fails fast.** `MainApp.prepareDatabase()` brings the schema up to date, loads demo data only with `LOAD_DEMO_DATA=true`, and runs the H2 migrations; any failure aborts the start. **PostgreSQL** is migrated by Flyway (`data/SchemaMigrator`, versioned files in `src/main/resources/db/migration/`, `V1__baseline.sql` creates the whole schema on an empty database; a database that has tables but no Flyway history is baselined at version 1; `SchemaMigrator` wraps the whole run in its own PostgreSQL advisory lock, because Flyway's baseline step runs before Flyway's lock and races when several instances start on an empty database; `SchemaMigratorTest` starts six instances fifteen times in a row). **H2** (desktop) gets `scheme-h2.sql` on an empty database and the idempotent `DatabaseMigration` deltas on every start (they run **only on H2**; identifier case differs: use the `table(...)` / `constraintExists(...)` helpers). `MainAppDatabaseTest` (H2 file DB), `PostgresStartupTest` and `SchemaMigratorTest` (real PostgreSQL, enabled by `POSTGRES_TEST_URL`) cover this.
- **Money:** amounts, quantities and rates are `BigDecimal` end to end (entities, DTOs, statistics, PDF, XRechnung, GoBD); no `double` arithmetic on money. `invoice.tax_rate` is stored as a fraction (`DECIMAL(5,4)`, 0.19) and exposed as a percentage (19.00) via `movePointRight(2)` / `movePointLeft(2)`. The server recomputes every line total as round(quantity) × round(unit price), rounded half-up to cents (`InvoiceItem.lineTotal`; the columns are `DECIMAL(10,2)`); a client-sent `totalPrice` is ignored. Tax and gross come from `VatCalculator` (per rate group, see **VAT per line**). PDF amounts are formatted with a fixed German locale (`1.234,56 €`), quantities without truncation (`1,5`).
- **Customers with documents cannot be deleted** (409 from `CustomerController`, and the database refuses too): `invoice.customer_id` is a restricting FK in all schemas (`migrateCustomerForeignKeyRestrict` replaces the old `ON DELETE CASCADE`, looking the FK up by its column through `KEY_COLUMN_USAGE` because H2's `REFERENTIAL_CONSTRAINTS` has no table column; it only runs on H2), and issued invoices must be retained.
- **Invoice lifecycle (GoBD)** — full rules in `docs/architecture/data-model.md > Invoice lifecycle`. Invoice types (1, 4, 5) are created as drafts **without number** (`document_number IS NULL`, API shows `ENTWURF`); `InvoiceLifecycleService.issue` (via `PATCH /status` → SENT) assigns the number from the invoice date's year, requires the Leistungsdatum and freezes `rendered_html`. Issued invoices and credit notes throw `DocumentStateException` (409) on update, delete and `from-document` re-layout; their PDF always comes from the snapshot. Payments are append-only (`payment`, reversals with negative amount + `reverses_payment_id`); status SENT / PARTIALLY_PAID (id **9**, not 7) / PAID and `paid_date` are derived from them. Cancelling creates a `CREDIT_NOTE` (type 6, prefix `ST`, `cancels_invoice_id`) with positive stored amounts (sign by type) that renders with the cancelled invoice's template. Invoices are never versioned; that path is for offers / cost calculations only. Every step writes `document_history`. Do not reintroduce client-supplied `paidDate` / `invoiceNumber` / status on `PUT`.
- **Offer / cost calculation lifecycle** — `DRAFT → SENT/ACCEPTED/CANCELLED`, `SENT → ACCEPTED/REJECTED/CANCELLED`, `REJECTED → ACCEPTED/CANCELLED`, `ACCEPTED → CONVERTED/CANCELLED`; `CONVERTED` and `CANCELLED` are final (table in `docs/reference/document-types.md`). `SENT` stays a status (the mail dispatch, once it exists, performs `DRAFT → SENT` and logs a history entry; it is not a separate notification). The table exists three times and one test file keeps them equal: `OfferStrategy.TRANSITIONS` (reused by `CostCalculationStrategy`), `OFFER_TRANSITIONS` in `frontend/src/utils/documentStatus.js` and `backend/src/test/resources/status-parity/transitions.json`, read by `OfferStatusTransitionsTest` and `useDocumentType.spec.js`. Change all three together. `PATCH /status` with the current status is a no-op (`200`); a refused change throws `InvalidStatusChangeException` (400 + JSON `message` naming the statuses). Invoice types are unchanged and still answer a bare 400.
- **Two migration systems.** PostgreSQL uses Flyway (see above): the schema is `src/main/resources/db/migration/V1__baseline.sql` (PostgreSQL: identity columns, `SMALLINT` flags, `CHECK` instead of `ENUM`, `set_updated_at()` triggers), and an applied migration is **immutable** (Flyway verifies its checksum on every start): every later change is a new `V2__...sql`. `DatabaseMigration` is the hand-rolled system for H2 only. There are two `scheme-h2.sql` files: `src/main/resources/scheme-h2.sql` is the seed used by the `desktop` / standalone Spring profile (`spring.profiles.active=desktop`) and uses **English** template names (`Default Invoice`, `Default Offer`, `Default Cost Calculation`, `Default Parted Invoice`); `src/test/resources/scheme-h2.sql` is the test-classpath seed and uses **German** template names (`Standardrechnung`, `Standardangebot`, `Standardkostenberechnung`, `Standardteilrechnung`). The two H2 files share the same block-JSON skeleton except that the desktop file adds `"dateFormat":"DD.MM.YYYY"` to the meta block config and `"columns":1` to the footer block config. Adding a new document type requires editing both H2 files **and** a Flyway migration for PostgreSQL (a new `V<n>__...sql`, or `V1` while nothing is released).
- **Seed templates.** The SQL seeds in `V1__baseline.sql` (PostgreSQL) / `scheme-h2.sql` insert `Standardrechnung`, `Standardangebot`, … when the database is created; nothing else creates templates at startup (new templates come from the editor's gallery, `templatePresets.js`). `de.billery.service.TemplateBlocksBackfill` (`@PostConstruct`, `@Profile("!saas")`) only writes the default blocks into templates whose `blocks` is empty, which is what the DOCX/ODT import stores.
- **SaaS profile.** Two switches, deliberately separate. The **Maven profile `saas`** (`mvn -Psaas ...`) adds Spring Security / OAuth2 resource-server and the folders `src/saas/java` (package `de.billery.saas`), `src/saas/resources` (Flyway location `db/migration-saas`) and `src/saas-test/java`; the default build contains none of it (CI checks the JAR) and surefire runs the whole suite with the Spring profile active in the `-Psaas` build. The **Spring profile `saas`** (`SPRING_PROFILES_ACTIVE=saas`) switches the behaviour on at run time: `SchemaMigrator` then also runs `db/migration-saas` with its own history table `flyway_schema_history_saas` (baselined at 0; separate numbering from the core), and the start fails with a clear message if the build lacks the SaaS code. The core never imports the SaaS package or Spring Security (`ArchitectureTest`, ArchUnit, meaningful in the `-Psaas` build). **Authentication (OIDC only):** `SaasSecurityConfig` is an OAuth2 resource server for the issuers in `billery.security.issuers` (env `BILLERY_SECURITY_ISSUERS`, comma-separated; at least one, plus the required `billery.security.audience`; the start fails without either); `TrustedIssuers` builds one decoder per issuer lazily (signature, expiry, issuer, audience; `TrustedIssuersTest`) and rejects any other issuer, so a second provider can be added next to the first. `/api/health` and the SPA's static files are open, everything under `/api` needs a token, `/uploads`, `/v3` and Swagger stay denied until tenant-scoped file storage exists. The authorization data lives in our tables, never in claims: `app_user`, `user_identity (issuer, subject) -> user`, `tenant_member (tenant, user, role)` (`V3__users_and_membership.sql`; `tenant_member` has forced RLS like the tenant tables, `app_user` / `user_identity` have none and are read only by identity, e-mail or user id). `IdentityService` maps a token to a user: a known identity needs nothing else; a new one needs a **verified** e-mail, which links it to the existing user of that address (the provider switch) or creates the user; an unverified address never links. `TenantContextFilter` (added after the bearer filter, deliberately not a bean) checks in the database that the user is a member of the tenant in `X-Tenant-Id` (optional for users with exactly one tenant; `/api/me` needs none), applies the role (`Role.allows`: a reader only reads) and sets `TenantContext`; its membership lookups run as the user because `tenant_member` shows a user its own rows. `GET /api/me` returns the user and the tenants with roles. History rows get `performed_by` from `app.user_id` through a column default. `TemplateBlocksBackfill` is `@Profile("!saas")` (startup has no tenant; templates are created per tenant at provisioning). **Tenant isolation:** `db/migration-saas/V2__tenant_isolation.sql` gives every tenant table a foreign key to `tenant`, the default `tenant_id = current_setting('app.tenant_id')::int`, and *forced* row-level security (`USING` and `WITH CHECK`); a missing setting raises an error (fail closed). `saas.db.TenantAwareDataSource` wraps the pool (`TenantDataSourcePostProcessor`, so the core only depends on `DataSource`) and sets `app.tenant_id` / `app.user_id` from `saas.tenant.TenantContext` when a connection is borrowed and clears them on return (a connection that cannot be cleared is aborted, never pooled again); `SaasCurrentTenant` reads the same context. The backend must connect as a login that is a member of `billery_app` (neither owner nor superuser nor `BYPASSRLS`), schema migrations as the owner (`DB_MIGRATION_USER`; `Database.migrationDataSource()`), connections direct or via a session-level pooler. A new tenant table needs a SaaS migration with the same four statements; `TenantIsolationTest` fails if a table with `tenant_id` lacks forced RLS and a policy. In the `-Psaas` suite everything runs as the app role with tenant 1 (`SaasTestSupport`); cleanup and fixtures use the admin account; core tests that assert the self-host schema or load demo data skip themselves under the profile. `AppProfiles` reads the profile before Spring starts; the SaaS build (it has `db/migration-saas` on the classpath) **refuses to start without the profile** (`requireProfileForBuild`, first call in `MainApp.main`), because the same JAR without it would run without authentication. Design: `docs/architecture/multi-tenancy.md`.
- **SaaS deployment kit.** `deploy/saas/` (compose file, `.env.example`, `postgres/init/10-roles.sh`, optional Caddy, `check.sh`, `backup.sh` / `restore.sh` (one implementation for this kit and the self-host stack: the source comes from the running backend container, the destination from `BACKUP_*`, runbook `docs/operations/backup-restore.md`), `generate-secrets.sh`) runs the `billery-saas` image against **any** OpenID provider: the provider is three values in `.env` and nothing in the kit is provider-specific. The init script creates `billery_owner` (owner, `BYPASSRLS`: `FORCE ROW LEVEL SECURITY` binds even the owner, the test suite migrates as a superuser and hides it), `billery_app` and `billery_login` (what the application connects as, bound by RLS) before the first start. `.github/workflows/saas-stack.yml` lints the scripts and starts the stack in CI with a mock provider (`deploy/saas/ci/`): `check.sh`, a journey with two users in two companies, a restart and a restored backup. Runbook: `docs/operations/saas-deployment.md`.
- **Isolation suite.** `saas/SaasIsolationTest` (extends `SaasApiTestBase`, the shared HTTP harness) must stay green in the `saas` CI job: it lists every `/api` endpoint of the running application and fails for one that is in none of its three sets (`attacks()` = tested with another tenant's real ids, `ACTS_ON_ACTIVE_TENANT` = creates or acts in the acting tenant only, `TENANT_FREE`). **A new endpoint needs an entry**; a new `BY_ID` / `LIST` attack needs a positive control (the same request must work for the owner of the data). Its positive controls call every endpoint as its owner, which also found two ordinary bugs (the PostgreSQL search mapper, the missing JAXB runtime). **`saas/SaasRoleMatrixTest` is the same guard for roles inside one tenant:** a new endpoint also needs a group there (`READ`, `WRITE`, `TEAM`, `OWNER_ONLY` or `NO_ROLE`); the group is the decision who may call it (a reader only reads, the team endpoints are for owner and admin, closing for the owner). Make both required status checks in the repository settings so they gate merges. The provider switch is documented in `docs/operations/saas-identity-provider.md` and tested by `IdpSwitchTest`.
- **Uploaded files.** `storage.FileStorage` (`save`, `read`: the bytes of a stored file, or `null`) is how uploads are stored and found; `FileUploadController` and the PDF renderer (`TemplateBasedPdfGenerator`, `RestrictedUserAgent` with an `UploadReader`) use only it. It returns bytes, never a `Path`, because the SaaS files may live in an object store. Self-host / desktop: `LocalFileStorage` (`@Profile("!saas")`), one flat directory `FILES_PATH`, URL `/uploads/<name>`, served by the static handler of `WebConfig`. SaaS: `saas.storage.TenantFileStorage`, object key `<tenantId>/<name>` in an `ObjectStore` chosen by `BILLERY_FILES_STORE` (`ObjectStoreConfig`): `local` = `DirectoryObjectStore` (`BILLERY_FILES_DIR` or `FILES_PATH`, default), `s3` = `S3ObjectStore` (AWS SDK v2, JDK HTTP client, only in the `-Psaas` build; a private bucket of any S3-compatible store, `BILLERY_FILES_S3_*`; several instances without a shared disk); a store that cannot be read throws, it never reads as "missing". URL `/uploads/<tenantId>/<name>?sig=<HMAC-SHA256>`; the static handler is **not** registered in the profile. An `<img>` cannot send a bearer token, so the URL carries the proof: `UploadSigner` signs tenant + file name with `BILLERY_FILES_SECRET` (required, 32+ characters; it does not expire because the URL is stored in templates, rotating the secret invalidates all of them) and `UploadController` serves a file only for a valid signature (checked before the file's existence is revealed), with the safety headers of `/uploads/**`. The renderer's `read` returns only files of the **active** tenant, so a template cannot make the server print another tenant's logo into a PDF. Purging a tenant does not delete its directory or bucket prefix (see the runbook); `backup.sh` / `restore.sh` follow `BILLERY_FILES_STORE` of the backend container (rclone for the bucket). Tests against a real S3-compatible store run with `S3_TEST_URL` (CI: SeaweedFS in the `saas` job; MinIO publishes no images any more).
- **Provisioning (SaaS).** `V4__provisioning.sql` adds `tenant.status` ACTIVE / SUSPENDED / CLOSED, `tenant_invitation` (RLS: the active tenant's administrators, plus the invited address for reading and accepting), a `tenant_create` insert policy (sign-up) and the operator function `purge_tenant(id)` (not granted to the app role; acts as the tenant, breaks the circular references, refuses tenant 1). `TenantProvisioningService.createTenant` first enforces the sign-up limits (`BILLERY_MAX_COMPANIES_PER_USER` 409, `BILLERY_SIGNUPS_PER_USER_PER_DAY` / `_PER_IP` / `_PER_DAY` 429, counted in `daily_quota` in the same transaction; the source IP is `request.getRemoteAddr()`, i.e. the first `X-Forwarded-For` address, which the proxy must overwrite; every refusal increments `billery_quota_refused_total{quota,scope}`, watched by the alerts `BilleryAbuseLimitReached` / `BilleryAbuseSuspected`; the SaaS test harness switches the sign-up limits off, `SignUpLimitsTest` on), then takes the id with `nextval`, switches to it with a transaction-local `set_config('app.tenant_id', ..., true)` (the new tenant must be visible to be inserted and returned), makes the caller OWNER and copies the default templates read as tenant 1 beforehand; `tenant_member` has **no** column default, always pass `tenant_id`. `InvitationService`: an invitation names an address (`TeamController` then mails it with `InvitationMailer` when `MAIL_*` and `BILLERY_PUBLIC_URL` are set; the link comes only from that setting, never from the request, and `InvitationMailQuota` limits the mails in 24 hours to 50 per user, 5 per recipient and `BILLERY_INVITATION_MAILS_PER_DAY` for the system, in `daily_quota` (`V7`, which replaced V5's `invitation_mail_quota`; `DailyQuota` is the shared counter), plus `BILLERY_INVITATION_MAILS_PER_IP` per source IP, checked and counted under an advisory lock so a refused attempt uses up nothing; a failed or unconfigured mail leaves the invitation in place and the answer's `mailSent` / `mailProblem` say so), the invitee accepts after signing in with that **verified** address (`app_user.email`, shipped to the database as `app.user_email`), in `NoTenantNotice` or, with a company already, in `AccountMenu`; the mail carries no token; queries always filter `tenant_id = :tenant` explicitly because the invitee policy would otherwise show another tenant's invitation addressed to the same person. `TenantAuditLog` writes every team action (invite, revoke, accept, role change, remove, leave, sign-up, close) to `tenant_audit` (`V6`, forced RLS, no UPDATE/DELETE for the app role; `document_history` has no UPDATE either) inside the transaction of the change; `GET /api/tenant/audit` (TEAM group) lists it. A new team action gets an entry and a line in `TenantAuditTest`. `MemberService`: an owner manages every role, an admin only accountant/reader, anyone may leave (the filter lets `DELETE /api/tenant/members/<own id>` through for every role and a closed tenant), the last owner stays (owners are locked `FOR UPDATE`). `RequestLimitFilter` (after `TenantContextFilter`, per tenant and instance) answers 429 + `Retry-After` above `billery.limits.requests-per-second` (default 20, burst 200) and for a third concurrent PDF / preview / XRechnung / export / import request of one tenant; the SaaS test harness switches the rate off. `TenantContextFilter` makes a CLOSED / SUSPENDED tenant read-only (GET works, so the GoBD export does). `/api/tenants` and `/api/invitations/**` need no `X-Tenant-Id`; `TenantContext` also carries the user's e-mail and role. Operator runbook: `docs/operations/saas-tenant-lifecycle.md`. **Data lifecycle and incidents:** `docs/operations/saas-data-lifecycle.md` is the operating policy for customer data (what is stored where, who reaches it, the 90-day export window after closing, the purge procedure with its register outside the database, backups, removing an account) and `docs/operations/saas-incident-response.md` the procedure for security incidents. Both state what the application does **not** record (sign-ins, reads, exports); a change to what is stored, logged, exported or deleted (a new table with personal data, a new log, a changed retention) must be reflected in them. `app_user` rows referenced by `tenant_audit.actor_id` or `tenant_invitation.invited_by` cannot be deleted (no `ON DELETE`): such accounts are anonymised, not deleted.
- **SPA sign-in (SaaS).** `GET /api/config` is open and tells the app its mode: `ClientConfigController` (`!saas`) answers `selfhost`, `SaasConfigController` answers `saas` plus the OIDC settings (`BILLERY_OIDC_CLIENT_ID` required, `BILLERY_OIDC_ISSUER`, `BILLERY_OIDC_SCOPE`, audience from `BILLERY_SECURITY_AUDIENCE`). `frontend/src/main.js` awaits `initAuth()` (`services/authService.js`) before mounting: self-host mounts at once and sends no headers; SaaS runs the authorization-code flow with PKCE (`oidc-client-ts`), keeps the **access token in memory only** (never in `localStorage` / `sessionStorage`; the PKCE state may live in `sessionStorage` during the redirect), reads `/api/me`, picks the active tenant (`billery.tenant` in `localStorage`, an id) and the shared `apiClient` interceptors add `Authorization` and `X-Tenant-Id`, renew once on 401 (then sign in again, never loop) and re-read the tenants once on 403. `services/session.js` holds the non-secret state; `AccountMenu` (navbar, actions only) switches tenants (store, reload), lists invitations to accept and signs out; `AccountSettings` (Settings → Konto) shows user, company and role; `NoTenantNotice` lets a user without a tenant accept an invitation or create a company (`teamService`, `openTenant`); `TeamSettings` (Settings, owners and admins) manages members, invitations and closing. Details: `docs/architecture/frontend.md`.
- **Tenant column.** `V2__tenant_id.sql` gives every tenant-owned PostgreSQL table `tenant_id INT NOT NULL DEFAULT 1`, makes uniqueness per tenant (number series, settings, document numbers, owner) and turns every foreign key into `(tenant_id, x_id) -> parent (tenant_id, id)` so one tenant cannot reference another tenant's row (foreign keys bypass row-level security). Repositories never mention `tenant_id`; self-host is tenant 1, H2 has no column. A new tenant-owned table needs the column, `UNIQUE (tenant_id, id)` if it is referenced, composite foreign keys and an `ON CONFLICT` that includes `tenant_id`; `ON DELETE SET NULL` needs a column list (PostgreSQL 15+). Design: `docs/architecture/multi-tenancy.md`.
- **Schema changes** for PostgreSQL are a new Flyway migration `src/main/resources/db/migration/V<next>__short_description.sql` (never edit an applied one, not even a comment: Flyway's checksum covers the whole file and the start fails; `AppliedMigrationsTest` compares every released migration, core and SaaS, with `src/test/resources/applied-migrations.sha256`, and a released migration gets a line there). The H2 side (desktop) needs both `scheme-h2.sql` files (new installs) **and** a `migrateXxx` method in `DatabaseMigration` (existing installs). Prefer `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` in the H2 methods.
- **`dummies.sql`** — two copies with distinct purposes:
  - `backend/src/main/resources/dummies.sql` — the bulk dummies file for PostgreSQL (deterministic; 1 owner, 100 customers, 15 equipment, 30 articles, 30 services, 16 number-series rows, 1 420 documents spread over 2023-2026, ~325 periods, ~3 160 root invoice items, ~570 sub-items, ~3 500 history rows, ~400 payment rows). It is what people see in demos: every customer name and catalog entry once, real umlauts, no "Demo"/"Dummy" texts, and history entries the application itself writes, consistent with each document's status (`SchemaMigratorTest.demoDataReadsLikeRealDataInADemo`, PostgreSQL only). Loaded by the application **only** when `LOAD_DEMO_DATA=true` (`DatabaseInitializer.loadDemoData`, after Flyway), and only into a database without customers. It uses explicit ids and ends with `setval` for the identity sequences. Never set the variable for real installs: the file also seeds number-series counters. For local development put `LOAD_DEMO_DATA=true` into `backend/.env`; to re-seed drop the volume (`cd backend && docker compose down -v && docker compose up -d postgres`) and restart the backend.
  - `backend/src/test/resources/dummies.sql` (H2) and `dummies-postgres.sql` (PostgreSQL) — minimal fixtures (number series + user settings), loaded explicitly by `TestDatabaseConfig`. The H2 one shadows the real `dummies.sql` on the test classpath, so a test that needs the real file reads it by path.
- **No Docker init scripts.** Both compose files start PostgreSQL empty; the backend creates the schema with Flyway on its first start (the root compose therefore starts with an empty customer table, the dev compose too unless `LOAD_DEMO_DATA=true` is set for the backend).
- **`logback.xml`** lives at `src/main/resources/logback.xml` and controls backend logging. Edit it to change log levels, patterns, or file output.
- **`java-dotenv`** loads `.env` from the **JVM working directory** at startup (i.e. `backend/.env` when running from that directory; see `AppConfig`). Docker uses environment variables instead.
- **PDF pipeline:** Two paths. Block-based: `TemplateBasedPdfGenerator` reads `InvoiceTemplate.blocks` JSON, walks 8 block types (`header`, `address`, `invoice-meta`, `line-items`, `totals`, `payment`, `notes`, `footer`), resolves **every** `{{variable}}` in every block from one `VariableContext` (unknown placeholders are removed), lays out half-width blocks (`config.width = "half"`) side by side (`layoutBlocks`), renders HTML, runs it through Flying Saucer (xhtmlrenderer) → PDF. Flying Saucer runs with `RestrictedUserAgent`: it loads only uploads (`/uploads/<name>` read from `FILES_PATH`, host/port ignored), `data:` images and its own classpath stylesheet — never the network or other files (template content is user input). Every PDF is PDF/A-3b: `font-family` always carries the generic family (`genericFontFamily`), and `pdf/EmbeddedFonts` maps the generic families to the embedded Liberation Sans / Serif / Mono (metrics of Helvetica / Times / Courier) by replacing Flying Saucer's built-in families under their names; OpenPDF refuses a font that is not embedded. `service/DocumentPdfService` decides which rendering a document's PDF gets (download and GoBD export) and turns issued invoices / credit notes with complete e-invoice data into **ZUGFeRD** (profile XRECHNUNG: `xmlgenerator/CiiGenerator` + `pdf/FacturXEmbedder`, PDFBox, attachment `xrechnung.xml`). `POST /api/templates/preview` renders an unsaved draft (sample document or `invoiceId`) through the same path for the editor's "PDF-Vorschau". Legacy: `InvoiceTemplate.htmlContent` with `{{variable}}` substitution (used for DOCX/ODT import/export round-trip via `DocumentConversionService`). **Note:** the `htmlContent` column is **not** consumed by the PDF renderer — it is a round-trip vehicle for DOCX/ODT import/export, and the SQL seeds write a placeholder HTML comment into it. The block-based path throws an exception if no block template exists for the document type — it does not fall back to the HTML path. The block JSON in the SQL seeds is the same across the four document types except that `header.data.invoiceTitle` (or `seed-meta.data.invoiceTitle` in the PostgreSQL seed) is set to `Rechnung` / `Angebot` / `Kostenberechnung` / `Teilrechnung` respectively. The PostgreSQL seed uses `seed-*` block ids; the H2 seeds use `h2-*` ids. `FINAL_INVOICE` is defined as a `document_type` row but has no `invoice_template` seed.
- **Per-document template override** — `invoice.template_id` (nullable) lets a single document override the type-default template. Resolved by `TemplateBasedPdfGenerator.loadTemplateForInvoice` at render time; a missing or empty override falls back to the type default with a warning. Saved-time `rendered_html` snapshots are regenerated through the same helper, so the snapshot stays consistent. The clone flow is **deferred to editor save**: `DocumentModal.openCustomize` only loads a template to populate the editor as a draft (the document's type default when no override exists, or the existing clone when one does); the clone row + `template_id` association + snapshot regeneration only happen on `onCustomTemplateSaved` via the `POST /api/templates/from-document/{documentId}` endpoint, which accepts an optional `templateData` body to apply the editor's draft in a single call. Cancelling the editor (or closing it via the dirty-state dialog's "Abbrechen" / "Verwerfen" buttons) leaves the document and the database untouched — no orphan row, no half-applied `template_id`. The PDF download endpoint (`InvoiceController.downloadInvoicePdf`) prefers fresh generation over the save-time snapshot when the invoice has a `template_id` — the snapshot's purpose (freezing the document at save time) is the wrong invariant for per-document overrides, where the user wants the latest version of the override template. Per-document clones are tagged with `invoice_template.is_document_specific = 1` and hidden from `GET /api/templates` by default; `GET /api/templates/by-type/{id}` always excludes them so the document modal's picker never offers another document's clone. The document modal's "Layout" section is in `DocumentModal.vue`; the per-document clones surface in the `/templates` view only when the "Dokument-spezifische Vorlagen anzeigen" toggle is on. `DocumentService.cloneDocument` inherits the source's `template_id` but does **not** duplicate the override template row. XRechnung is data-driven and ignores the override (it has no concept of a "template"). The SPA's "Layout" section has two confirmation guards to prevent accidentally discarding a per-document override: clicking the "Standardvorlage für diesen Dokumenttyp" radio on a document that already has an override asks for confirmation (`DocumentModal.onLayoutModeDefault`); the `submit()` method also catches every other path that could silently null `templateId` (Guard D in `DocumentModal.submit`, a safety net for stale modal resets, dropdown deselects, etc.). The backend has no opinion — it just persists what the SPA sends. **Editor edits to the override are persisted by the SPA, not the editor itself**: `TemplateEditor` only emits a `save` event with the edited form; `DocumentModal.onCustomTemplateSaved` is responsible for forwarding it. The handler dispatches on `editingIsNewOverride`: when the document had no override yet, the handler calls `templateAPI.cloneForDocument(invoice.id, sourceId, savedTemplate)` (single round trip: the server creates the clone, applies the editor's content, persists `template_id`, regenerates the snapshot); when the document already had an override, the handler calls `templateAPI.updateTemplate(form.value.templateId, savedTemplate)` and the editor's edits land on the existing clone. The editor's local form has no `id` field; the URL path parameter is the source of truth. Forgetting the `updateTemplate` call is a silent no-op — the clone's `blocks` / `cssContent` stay byte-for-byte equal to the source, and the PDF keeps rendering the global look. This was the 2026-06-20 bug. **The editor's form must round-trip the `documentSpecific` flag** (carried in `templateData`); the controller's `convertFromDto` would otherwise default a missing flag to `false` and silently demote a per-document clone to a global one on the first save. This is verified by `TemplateEditor.spec.js > emits documentSpecific in the save payload` and `DocumentModal.spec.js > onCustomTemplateSaved calls updateTemplate with the clone id and the editor form`.
- **Per-document override cleanup** — Deleting a template via `DELETE /api/templates/{id}` nulls `invoice.template_id` on every referencing invoice (`InvoiceRepository.nullTemplateIdForTemplate`), so the renderer falls back to the type default at PDF time (with a warning logged by `loadTemplateForInvoice`). Deleting a document via `DELETE /api/invoices/{id}` cleans up the document's per-document clone row (if any) — the controller only deletes `invoice_template` rows where `is_document_specific = 1`, so a global template that happens to be referenced is left alone. Net effect: no orphan clone rows after document delete, no dangling `template_id` integers after template delete.
- **Live preview in the per-document editor** — `DocumentModal.openCustomize` builds a `liveData` object (`variables`, `totals` with the server's `vatGroups` and the legal note, `items` with per-line `taxRate`, `invoiceId`) via `buildPreviewVariables` / `buildLineItemsData` in `utils/invoiceVariables.js` and passes it as the `:live-data` prop on `TemplateEditor`. It only enters the preview context (`utils/previewData.js > buildPreviewContext`: sample → owner → live); the saved `blocks` JSON is never mutated with the real-document values, so per-document clones don't leak their source's data into the stored template. With `liveData` the editor hides the document-type select and the "Standard" checkbox.
- **Template editor model** — details in [`docs/reference/editor.md`](./docs/reference/editor.md). `form.blocks` array order **is** the block order (`order` is read once by `blockModel.normalizeBlocks` and written by `serializeBlocks`; never sync both while editing). The selection is an id; `BlockConfigPanel` emits a changed copy of the block and keeps no copy of its own. Undo/redo (`useHistory`) and the unsaved-changes guard watch `form`. Saving is blocked by `blockValidation.js` errors (required `invoice-meta` / `line-items` / `totals`, `limits.max`). Template CSS reaches the preview only through `scopeCss`.
- **Renderer parity** — the editor preview (`blockRegistry.js` `render`, via `renderBlockPreview.js`) and the PDF (`TemplateBasedPdfGenerator.render*`) are two implementations of the same markup. `backend/src/test/resources/template-parity/cases.json` is rendered by `TemplateParityTest` (Java) and `frontend/src/utils/templateParity.spec.js`; both must show the same texts and styles. Any block or format change goes into both renderers plus a parity case.
- **XRechnung:** `xmlgenerator/XRechnungGenerator` writes XRechnung 3.0 UBL (`ubl:Invoice` 380, `ubl:CreditNote` 381 with `BillingReference`) and is **pure** — `EInvoiceService` loads the data and serves `GET /api/invoices/{id}/xrechnung` (409 listing missing master data) and `/xrechnung/check`. Issued documents use the seller/buyer frozen in `invoice.party_snapshot` at issue (`PartySnapshot`), not live `Customer`/`Owner`. It does not consult the block template. Sub-items are flattened into separate lines; `CUSTOM` notes become the line note of the line above. Seller and buyer are assumed to be in Germany (no country field). `CiiGenerator` writes the same XRechnung in CII syntax for the ZUGFeRD PDF (same data, rules and required fields; `ZugferdTest` compares the attached XML with the UBL in 36 business terms and with the text on the page, so a new field goes into both generators and `ZugferdTest.FIELDS`). Any generator change must keep `VatAndEInvoiceTest#generatedXRechnungsPassTheKositValidator` and `ZugferdTest` green (the `xrechnung` job also validates the attached XMLs with KoSIT and the PDFs with veraPDF) — it runs in the `xrechnung` CI job against the KoSIT validator fetched by `scripts/fetch-kosit-validator.sh` (`XRECHNUNG_VALIDATOR_DIR`).
- **VAT per line:** `invoice_item.tax_rate_percent` (percent, 19 or 7) and `invoice_item.unit` are stored per line; `invoice.tax_treatment` (`STANDARD`, `SMALL_BUSINESS`, `REVERSE_CHARGE`, `TAX_EXEMPT`) decides whether VAT is charged; `invoice.tax_rate` is only the default for lines without a rate. **All amounts come from `tax/VatCalculator`** (grouped by rate, rounded once per group) — API, payments, statistics, PDF, XRechnung, GoBD export. Never compute tax from `invoice.tax_rate` or `Invoice.getTaxAmount()` (that is only correct after the renderer sets `computedTaxAmount`). `SMALL_BUSINESS` is forced exactly when the owner is a Kleinunternehmer. `migrateVatPerLine` backfills existing data once, guarded by the `user_settings` row `migration_vat_per_line`.
- **GoBD export:** `GET /api/export/gobd?from&to&documents` (`ExportController` → `GobdExportService`) returns a ZIP of CSV tables + GDPdU `index.xml` (`GobdIndex`, whose column lists must match the CSV headers, and which must stay valid against the GDPdU DTD in `src/test/resources/gdpdu/` — `GobdExportTest` checks both) + PDFs/XRechnungs. The whole ZIP is built in memory, so `export()` is bounded (`configureLimits`, `export.*` properties, defaults in `docs/reference/env-vars.md`): the period is selected in SQL (`InvoiceRepository.findByInvoiceDateBetween`, never `findAll()`), too long a period / too many documents / a ZIP above the byte limit throw `ExportLimitException` (HTTP 413, never a truncated export: the export must stay complete), and a busy slot throws `ExportBusyException` (429 + `Retry-After`); the slot is released in a `finally`. The SPA shows the message because the axios interceptor reads it out of the blob error body. The German process documentation for the business lives in `docs/operations/verfahrensdokumentation.md`.
- **Sub-items (line-item tree):** `invoice_item.parent_item_id` is a self-FK with `ON DELETE CASCADE`. `InvoiceRepository.nestInvoiceItems` flattens the row set into a tree on read; `DocumentService.saveItems` / `saveChildItems` / `cloneItemTree` do recursive DFS inserts. **Sub-items stand on their own in v1** — the parent line's `totalPrice` does not roll up its children; both contribute independently to `netAmount` / `grossAmount` via `sumItemsRecursive`. The PDF path (`TemplateBasedPdfGenerator.renderItemRow`) walks the tree and renders child rows indented. The editor (`DocumentModal.vue` + `editor/InvoiceItemRow.vue`) and the view modal (`DocumentViewModal.vue`) expose the tree in the UI. The XRechnung path does not.
- **`item_type = CUSTOM` is a free-text note, not a priced line.** It is only allowed as a sub-item (root rows are always `ARTICLE` or `SERVICE`). The application layer forces `quantity=1`, `unit_price=0`, `total_price=0`, `unit=""` on every save (`DocumentService.buildItem` + `InvoiceRepository.saveInvoiceItem`); the editor hides pricing inputs and the PDF renders the qty / unit / price columns as em-dashes for that row. `item_name` and `item_description` are persisted in `invoice_item` so the note survives a round-trip (`DatabaseMigration.migrateAddItemNameAndDescription`).
- **Test DB:** `TestDatabaseConfig` sets up H2 in-memory with MariaDB compat mode (`jdbc:h2:mem:testdb;MODE=MariaDB`, test schema `src/test/resources/scheme-h2.sql`), or, when `POSTGRES_TEST_URL` is set, resets the `public` schema of that PostgreSQL, runs Flyway (`SchemaMigrator`) and applies `dummies-postgres.sql` (`clearData` then uses `TRUNCATE ... RESTART IDENTITY CASCADE`). Start a throwaway `postgres:17` for it; the database is wiped.
- **Typed parameters:** PostgreSQL rejects `varchar` parameters for `DATE` columns, so repositories bind dates with `BaseRepository.dateOrNull(isoString)` (a `LocalDate`; entities and DTOs keep ISO strings) and never rely on the driver converting strings. Use `CAST(x AS VARCHAR(n))`, never `CAST(x AS CHAR)`, and `MERGE` (not `ON DUPLICATE KEY` / `ON CONFLICT`) for upserts that must run on H2 too.

## Template System Rules (critical domain logic)

- **NO HARDCODED FALLBACKS** — applies to the **render path** only. If no template exists in DB, throw an exception. Never substitute placeholder data. The template editor's preview uses sample data (`SAMPLE_DATA`, `previewData.js`) — do **not** apply the same rule to the editor preview. But block **defaults** are stored in templates and printed: new blocks hold `{{variables}}`, never sample literals (the old `INV-2026-001` defaults were printed on real invoices; `migrateTemplateSampleLiterals` and `migrateBlock` repair them).
- **USE ONLY USER-CONFIGURED DATA** — if a template field is empty, don't render it. Don't fall back to owner/customer data.
- Template variables use **German names** in `{{curly_braces}}**: `{{firma}}`, `{{kunde}}`, `{{rechnungsnummer}}`, `{{betrag}}`, etc. Full list in [`docs/reference/variables.md`](./docs/reference/variables.md). Note: the block-based template path uses German names; the legacy `htmlContent` path (DOCX/ODT round trip) also uses lowercase German names (`{{firma}}`, `{{kunde}}`, `{{positionen}}`, `{{netto}}`, …). The canonical date variables in the block registry are `rechnungsdatum` and `faelligkeitsdatum`. `DocumentController.getAvailableVariables()` returns English/uppercase names (`OWNER_COMPANY`, `INVOICE_NUMBER`, `NET_AMOUNT`) for the DOCX/ODT import picker; the uppercase list is a hard-coded alias and is not bridged to the German registry at runtime.
- Block types are described completely in `src/utils/blockRegistry.js` (`defaultData` / `defaultConfig`, `fields` / `settings` for the generated config panel, `limits`, `formatDefaults`, preview `render`). A new config option goes into `defaultConfig` **and** `settings` (`blockRegistry.spec.js` fails otherwise), into the JS `render` and the Java `render*` method, plus a parity case. `BlockConfigPanel.vue` needs no change.
- **Variables in the editor are chips** (`VariableTextInput`): users never see `{{braces}}`; labels and groups come from `variableRegistry.js` (`getPickerGroups`, `getChipLabel`, `isKnownVariable`). Spaces inside the braces are ignored by both renderers.
- **Editor dirty state** — `src/composables/useUnsavedChangesGuard.js` is the canonical place for any new in-modal editor. The composable returns `requestClose(): Promise<'save'|'discard'|'cancel'>` so editors can map each action to the right emit, plus an `isDirty` computed and a `showConfirm` ref. Parents must forward their cancel / backdrop-click handlers to the editor's exposed `requestClose()` method instead of closing the modal directly. The guard must be stored on the instance with `markRaw()` in Options API to keep the inner refs from being auto-unwrapped by the component's reactive proxy. The dialog itself is rendered inside the editor at `z-index: 1100`, above the parent modal's `z-index: 1000`.

## Docker

- `docker-compose.yml` (root) — full stack: postgres + backend (the backend image also contains the built SPA, `backend/Dockerfile` has the repo root as build context; the old separate `frontend` service is the optional `split` profile). The database starts empty and the backend migrates it with Flyway, so a fresh install has the schema and an empty customer table. This is the production-like layout.
- Both production compose files (root and `deploy/saas/`) harden and limit the containers: the backend is `read_only` (writable: `uploads` and `logs` volumes, tmpfs `/tmp`), `cap_drop: [ALL]`, `mem_limit` `BACKEND_MEMORY_LIMIT` (heap 75 % via `-XX:MaxRAMPercentage=75` in `backend/Dockerfile`), `cpus`, `pids_limit`; PostgreSQL keeps five capabilities; console logs rotate (`x-logging`). Health checks use `/api/health/ready` (database included, answers within 3 s). Metrics: Actuator + Micrometer Prometheus at `/prometheus` on `BILLERY_METRICS_PORT` only (`management.server.port`, default `-1` = off; `management.endpoints.access.default=none`, only `prometheus` read-only), alert rules and their `promtool` tests in `deploy/saas/monitoring/` (CI job `saas-kit`); `/api/health` stays the liveness check the desktop shell needs. A new endpoint that is open in SaaS goes into `SaasSecurityConfig` and the `TENANT_FREE` / `NO_ROLE` sets. Details: `docs/operations/ops-gotchas.md`.
- `backend/docker-compose.yml` — PostgreSQL only (local dev, port 5432). The database starts empty; set `LOAD_DEMO_DATA=true` in `backend/.env` for the full 2023-2026 demo dataset.
- The app (SPA + API, one origin) runs on port 8080, published on `${BIND_ADDRESS:-127.0.0.1}:${APP_PORT:-8080}` (root `.env`, see `.env.example`); the optional `split` frontend on 5173 (static `serve -s dist`). Behind a reverse proxy nothing else is needed, but the proxy **must** send `X-Forwarded-Proto`/`-Host` (`server.forward-headers-strategy=framework`); without them even same-origin requests get 403 "Invalid CORS request". The app has no authentication: keep it off public interfaces or protect it in the proxy. The root compose does **not** publish PostgreSQL's port; the dev compose does (5432). The backend image runs as user `app`; uploads go to the `uploads` volume (`/app/uploads`).

## CI (GitHub Actions)

The workflows in `.github/workflows/` are the source of truth. Non-obvious points:

- `maven.yml`: `mvn verify` (tests, JaCoCo, Spotless check, PMD check), a `postgres` job that runs the whole backend suite against a PostgreSQL service container (`POSTGRES_TEST_URL`) **only when the self-host schema, its migrations, demo data or the database bootstrap change** (everything else on PostgreSQL is covered by the next job), a `saas` job that runs the whole suite with `-Psaas` on PostgreSQL (plus a SeaweedFS container as S3-compatible store, `S3_TEST_URL`), a step that fails the `build` job if the self-host JAR contains SaaS code or Spring Security (pull requests run these checks for any base branch), and an `xrechnung` job that validates generated XRechnungs with the KoSIT validator (`scripts/fetch-kosit-validator.sh`, official release, checksummed) (only when e-invoice, PDF, VAT code or the validator change). The `backend-changes` job decides; a push to `main` after a merge runs only `build`.
- `frontend.yml`: `npm ci`, `npm run test:run`, `npm run build` (job `frontend-test`). `maven.yml` and `frontend.yml` start on **every** pull request, deliberately without a `paths` filter on `pull_request`: they are meant to be required status checks, and a required check that never starts leaves the PR waiting forever (the `push` trigger keeps its filter). Instead `maven.yml` has a `backend-changes` job, and `frontend-test` / `e2e-smoke` / `dependency-scan` check the changed files in their first step and skip the rest (one billed job instead of two); a job skipped by its condition, or one whose steps are skipped, counts as passed. E2E ignores tests, unit specs and Markdown; the dependency scan runs for manifests and lockfiles, the image scans for Dockerfiles and the dependencies that go into an image; `saas-stack` runs only for the kit, the Dockerfile, `pom.xml`, the SaaS code and migrations (weekly on `main`). Keep the patterns of these jobs in step with what a workflow really tests. **Actions minutes are limited:** every pull-request workflow has `concurrency` with `cancel-in-progress` for pull requests, SAST, Gitleaks, E2E and the security scan do not run again on `main` after the merge (SAST and Gitleaks scan `main` weekly instead, for direct pushes), Pages deploys weekly, Dependabot proposes monthly. Push fixes to a pull request in one go, not one push per review comment. **Rules for agents:** see *CI budget* below.
- `e2e.yml` (job `e2e-smoke`): packages the app like `backend/Dockerfile` (built SPA inside the `-Pdesktop` JAR), starts it on an empty in-memory H2 and runs the Playwright suite in `frontend/e2e/` (`npm run test:e2e`, `E2E_BASE_URL`). It fails on console errors, CSP violations and `/api` responses >= 400, so header or filter changes that break a screen show up here; a new screen or flow should get a step in `smoke.spec.js`. Starts on every pull request, no `paths` filter (its first step skips the rest when nothing of the product changed: tests, unit specs and Markdown do not count, the smoke suite itself does); no run on `main` after the merge.
- `security.yml` (jobs `dependency-scan`, `image-scan (backend|frontend)`): Trivy over the manifests and lockfiles and over the two Docker images; fails on HIGH or CRITICAL **with a fix**, the weekly run writes the full report to the job summary. Accepted findings go into `.trivyignore` with a reason and an expiry date. `release.yml` (tag `v*.*.*`) runs `mvn verify`, builds and scans the image (a finding blocks the release), pushes **two images** to **GHCR** (`ghcr.io/billery-app/billery` self-host and `ghcr.io/billery-app/billery-saas`, private packages; tags `1.2.3`, `1.2`, `latest`, a hyphenated tag only its own). `backend/Dockerfile` builds both (`--build-arg MAVEN_PROFILES=saas SPRING_PROFILE=saas` for the SaaS one, which has the Spring profile `saas` built in: a SaaS JAR without it would run without authentication); `scripts/check-image-variant.sh` checks each image is the variant it claims to be and creates a **GitHub** release with the JAR, CycloneDX SBOMs, the scan report, the image digest and checksums. The `build` job has a read-only token; `publish` pushes the very image that was scanned. Policy and workflow: `docs/operations/supply-chain.md`. Java 25 and Node 24 are the one version everywhere (pom, workflows, Dockerfiles, desktop runtime).
- `pr-sast.yml`: `semgrep scan --config auto --error` over the whole repo; exclusions in `.semgrepignore`. Two rules are excluded on purpose (action version tags, Dependabot cooldown). Reviewed `v-html` uses carry a `nosemgrep` comment with the **full** rule id (`...avoid-v-html.avoid-v-html`).
- `llm-review.yml`: advisory LLM security review of pull requests (one edited comment, never a required check). It runs only when the actor is the maintainer named in the workflow (`REVIEWER_LOGIN`), the PR comes from the same repository and the head commit has a verified signature by that author; the diff (minus lockfiles, demo data, generated files, docs) goes to `<LLM_ENDPOINT>/chat/completions` (`LLM_ENDPOINT` is a repository variable holding the base URL of an OpenAI-compatible API, default GitHub Models API) with the secret `LLM_API_TOKEN`. The PR content is untrusted: it only travels through files and env vars, the model has no tools.

## CI budget (Actions minutes are limited)

A pull request run costs roughly 15–40 runner minutes (every job is rounded up to a whole minute),
and agents that push often use them up quickly. So:

- **Fewer, larger pull requests.** Bundle related work; do not open one PR per small step. Run
  the checks locally first (`mvn verify`, `mvn -Psaas verify` against a throwaway PostgreSQL,
  `npm run test:run`, KoSIT / veraPDF where relevant), so CI confirms instead of discovering.
- **One push per review round.** Collect every fix (review comments, CI failures) and push once;
  every push restarts all workflows of the pull request.
- **No blind re-runs.** Read the failing log first. Re-run only a single failed job, and only when
  the log shows an outside cause (a mirror or registry that did not answer); never re-run a whole
  workflow "to see". A cause that persists gets a fix in the workflow, not a second re-run.
- **Dependabot:** ask for rebases only once the fix they need is on `main`, and handle several
  dependency pull requests in one go.
- **Before adding a job or widening a trigger,** say what it costs per run and why the existing
  jobs do not cover it; prefer the weekly schedule for slow checks that rarely find anything.
- **When the budget is used up,** say so instead of pushing more; work continues locally.
- **Every job has `timeout-minutes`** (about three to four times its usual duration), so a hung
  job ends instead of running for GitHub's default six hours; a new job gets one too.
- **Usage:** the organisation's Settings → Billing and licensing → Usage.

## Before Submitting Changes

```bash
# Backend (from backend/)
mvn spotless:apply && mvn verify

# Frontend (from frontend/)
npm run test:run
```

### Verification before a PR (applies to every change, human or agent)

A green CI only proves what the tests cover. Before opening or updating a PR:

- **Run it yourself.** Build and test locally; if the toolchain is missing, install it or say so
  in the PR instead of relying on CI as the only feedback. "Diff manually reviewed" is not
  verification.
- **Exercise the change in the running app**, not only in unit tests: start it and use the
  affected feature and the features next to it. A change that touches every request or response
  (filters, headers, error handling, config, dependencies) can break any screen, so check the
  main flows (PDF preview/download, import/export, saving a document), not just the changed code.
- **Look for what the change can break outside the diff.** Search the codebase for callers and
  consumers of what you changed (frontend code, desktop shell, tests, docs); the files that
  break are usually not in the diff.
- **Test the success path as well as the rejection path.** A validation or security check needs
  a test that valid input still passes, with a realistic input.
- **Treat tests that had to be adapted as a warning.** If existing tests fail after your change
  and you edit them to fit, first decide whether the change or the test is wrong.
- **State in the PR what was verified and what was not.** Unverified parts are listed, not
  glossed over.

## Documentation Maintenance

- **Update docs in the same pass as the change.** After every
  user-verified and accepted code change or enhancement, update
  the relevant files in `docs/` (`docs/README.md`,
  `docs/architecture/*.md`, `docs/guides/*.md`,
  `docs/reference/*.md`, `docs/operations/*.md`, this `AGENTS.md`
  at the repo root, and the top-level `README.md`) directly — do
  not defer the doc edit to a later commit.
- **No documentation drift.** If a change alters a documented fact (versions, file layout, env vars, commands, architecture, modules, controllers, repositories, env-var names, etc.), the matching doc line must be edited before the change is considered complete. Stale docs are treated as a bug.
- **No new "TBD" / "TODO" placeholders.** If a fact is unknown, either find it before claiming to be done, or leave the previous fact untouched and flag the uncertainty in the response to the user — never invent a placeholder that will rot.
- **Document your codebase**: Everytime you change code snippets, document them directly with good readable JavaDocs or the equivalent in other languages.
